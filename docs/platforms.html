Platforms#

Burrow v1 targets the desktop: Windows, macOS and Linux, on x64 and ARM64, all through Vulkan (MoltenVK on macOS). Web and mobile are out of scope for now. This page states what is verified and what is not, because "it builds" and "it runs" are different claims.

Requirements#

All platforms: a GPU and driver exposing Vulkan 1.2 or newer with the 1.3 features dynamicRendering and synchronization2 (the engine asks for 1.3, falls back to 1.2 with those features, and refuses a device without them). Rough guide, not a tested list: a GPU from roughly 2015 or later with a current driver (NVIDIA Maxwell and newer, AMD GCN and newer, Intel Skylake and newer), every Apple silicon Mac. If vulkaninfo --summary shows a Vulkan 1.3 device, Burrow should start.

How the Vulkan loader is found#

The lookup runs before the loader starts (internal/vkenv, used by window.Init).

macOS, first match wins for the loader (libvulkan.1.dylib) and the MoltenVK driver manifest (MoltenVK_icd.json):

  1. BURROW_VULKAN_LIB (absolute path of the loader file) and an already set VK_ICD_FILENAMES or VK_DRIVER_FILES (never overridden).
  2. BURROW_VULKAN_DIR (a folder laid out like one of the places below).
  3. The app bundle: Contents/Frameworks, Contents/Resources/vulkan.
  4. Next to the executable, and lib/ beside it.
  5. System: /opt/homebrew/lib, /usr/local/lib, ~/VulkanSDK/macOS/lib.

When a driver manifest is found the engine exports VK_ICD_FILENAMES and VK_DRIVER_FILES for the process; when only libMoltenVK.dylib is found it writes a manifest into a private temporary folder. Executables do not link MoltenVK: nothing in a shipped binary points at /opt/homebrew. The loader is opened by absolute path only (a bare name would let dyld search the working directory).

Linux: the system loader libvulkan.so.1 (no bundled copy). BURROW_VULKAN_LIB can point at another loader. Windows: System32\vulkan-1.dll only, overrides are ignored on purpose (DLL search-order hijacking).

When no driver is found the editor, the Hub and burrowplay print the install hint to stderr and, on Windows and macOS, show a message box. On Windows the same text lands in the log file. burrow doctor runs the same checks ahead of time (loader, driver, display server, platform).

Display scaling (HiDPI)#

The Hub, the editor and runtime windows follow the display scale of the system, so the interface has a normal physical size on a 4K monitor.

  • Automatic (default). The window asks the system for its content scale (Windows display scaling per monitor, Xft.dpi on X11, the output scale on Wayland, the Retina factor on macOS), rounds it to the nearest step (100, 125, 150, 175, 200, 250 or 300 percent) and lays out and rasterises text, icons and borders at that size, so glyphs stay sharp. Moving a window to a monitor with another scale re-lays it out at once.
  • Setting. Hub: Settings, Display, UI scale (ui_scale in hub.json). Editor: Preferences, UI scale. A fixed value is a percentage of the platform's logical size: 100 is normal on a 1x display and on macOS (where the Retina factor is added on top), 150 is one and a half times larger than that.
  • Shortcuts. Ctrl and plus, Ctrl and minus, Ctrl and 0 (Cmd on macOS) in the Hub and the editor: larger, smaller, back to automatic. The choice is saved.
  • Environment. BURROW_UI_SCALE (auto, 150, 150% or 1.5) overrides the setting. On Linux, when the window system reports no scaling at all, GDK_SCALE and QT_SCALE_FACTOR are used as a hint. The scale never goes so high that the window holds less than 800 by 480 logical pixels.
  • Window size. A window without a requested size covers about 70 percent of the work area of the primary monitor (at least 960 by 600 logical pixels), centred. Position and size are remembered per window in <user config dir>/burrow/window/ and restored only when the window is still on a connected monitor.
  • Windows. Every executable embeds an application manifest that declares per-monitor DPI awareness v2, long path support and the requested execution level asInvoker (no administrator rights), together with a version resource (company, product, description, version, copyright). Without the DPI declaration Windows would stretch the window as a bitmap. The sources are in assets/winres/.
  • Game HUD. gameui scales with the window height (reference 720 px), so it grows with the resolution; its Scale option multiplies that.

Determinism across platforms#

StateHash is meant to be the same on every OS and CPU; verified today on macOS Apple silicon and Intel (Rosetta), while Windows and Linux are checked by the CI workflow against the golden hash, which has not run yet. The simulation (voxel world, water, the standard game rules, 2D and 3D physics, navigation, animation, weather, scripts) uses integer math where it can, and its float math rounds every product explicitly and takes its trigonometry, exponentials and logarithms from a deterministic library instead of the platform's. scripts/portability-hash.sh runs the eight templates for 200 ticks and compares the hashes with the committed golden (scripts/portability-golden.txt); every CI job runs it. On one Mac the arm64 and the amd64 (Rosetta) binaries give identical hashes for all eight templates at 200 and 2000 ticks; the other operating systems are verified by CI once it has run. Rendering and other frame-domain code is not covered and does not need to be. Details, guards and rules for contributors: Determinism.

Known limits#

  • Graphics: the windowed engine has been run on one GPU family (Apple M2 Max through MoltenVK). Other drivers (NVIDIA, AMD, Intel, Mesa) may expose driver bugs or missing features the renderer has not met.
  • Windows binaries are not code signed and Microsoft SmartScreen warns on first run; macOS apps are ad-hoc signed and not notarised, so Gatekeeper asks for confirmation.
  • Clipboard: macOS uses the system clipboard through pbcopy/pbpaste; Windows and Linux use GLFW's clipboard (new in this version, untested on those systems).
  • Audio on Linux needs PulseAudio, PipeWire-Pulse or ALSA at run time.
  • Wayland sessions run through XWayland (X11 build of GLFW).
  • Software rendering (lavapipe, WARP) works for smoke tests but is far too slow to play.
