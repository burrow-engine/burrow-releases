Go game (package gogame)#

A project's game logic can be a plain Go main package that imports burrow-engine/gogame. The project folder still holds the scenes, prefabs, input map and assets (vox.project); only the logic moves from WebAssembly scripts to your own Go code, with full access to the engine.

Go game or WASM scripts?#

Go game (gogame)WASM scripts (script)
Trusttrusted, native codesandboxed, gas-metered
Deliveryone Go binary next to the project.wasm modules inside the project / pak
Engine accesseverything (Ctx.App(), any Go package)host functions only, JSON features
Statepackage variables persistmemory reset on every call; state lives in components
Editorburrow edit shows scenes, but the logic is not hot reloadedhot reload, debugger, script panel
Mods / untrusted contentnoyes

Pick the Go game for your own game with an AI agent or a Go programmer at the keyboard. Pick WASM scripts for mods, user-made content and anything that must run in the editor with hot reload.

Quick start#

burrow new mygame --template gogame
cd mygame
go run .                  # window
go run . -headless 100    # 100 ticks, one JSON line {"ok":true,"ticks":100,"hash":"...","error":""}

vox.project keeps "scripts": []. No scripting plugin is needed: the journaled input snapshot behind Ctx.Action comes from input/inputsnap (older projects that still enable plugins.scripts keep working; the script plugin then produces the same snapshot). Flags of gogame.Main: -dir, -scene, -headless N, -saves.

func main() {
    gogame.Main(gogame.Game{
        OnStart: func(c *gogame.Ctx) error { return nil },
        OnTick:  func(c *gogame.Ctx) { if c.ActionPressed("stamp") { c.SetVoxel(1, 9, 1, "wood") } },
        OnFrame: func(f *gogame.Frame) {},
        UI:      func(ui *imui.UI) { ui.Label("hello") },
    })
}

examples/gogame_demo scaffolds the template and runs it. gogame.RunHeadless(game, gogame.Options{Headless: n}) returns the Result (with StateHash and the finished App) for tests.

Determinism#

OnStart and OnTick run inside the fixed step (20 Hz) after the engine's own fixed systems. Their changes are part of the simulation state, so a run replays to the same StateHash when your code is deterministic: use Ctx.Rand (never math/rand globals), no wall clock, no map-order dependence, no reads of data outside the simulation. Package variables persist but are not saved or rolled back. OnFrame and UI are per rendered frame and cosmetic. A failing call (unknown block, bad component JSON) is returned as the tick's error and stops the run.

Game state#

Package variables are not saved or rolled back, so a game keeps its rules (inventory, timers, quests, health, hunger) in Ctx.State: named values stored in one simulation component. They are hashed, snapshotted, saved, rolled back and replayed with the world, with no node and no script. Values are JSON (SetState/State/StateOf) or raw bytes (SetStateBytes/StateBytes, for a binary format of your own). Limits: 256 keys, 1 MiB per key, 4 MiB in all; unchanged writes cost nothing. Use structs, not maps, in JSON you hash. The engine gives the state no meaning: health, death and respawn are rules of the game, written in OnTick.

Multiplayer note: the whole state is one component value, and a server sends a component value only when its JSON is at most 64 KiB (wire.MaxCompData; bytes are base64, so about 48 KiB of blobs). A game whose state is larger works the same in solo and on the authoritative side, but its state is not mirrored to remote clients; keep what a client must read small.

type Vitals struct{ HP, Food int }

OnTick: func(c *gogame.Ctx) {
    v := gogame.StateOf[Vitals](c, "vitals")
    if c.ActionPressed("eat") { v.Food++ }
    _ = c.SetState("vitals", v)
}

Network games#

A Go game can run as a dedicated server and be played from the game's own window. There is no listen server: nobody hosts from a window.

./game -init-server ./srv        # writes srv/server.json and the TLS certificate (Game.Dir is the project)
./game -serve ./srv              # prints "join link: burrow://host:7777?fp=...&key=..."
./game -connect "burrow://..." -name ana

Game.NetScene is the scene the server runs and the clients follow. The server alone runs OnTick; a client runs only frame systems (OnFrame, UI) on the replicated copy, and a dedicated server runs neither. So:

  • Loop over c.Players() in OnTick (one player, id 0, when the game is played alone), read a player's input with c.ActionOf(p, name) (in a session an action is a button bit: move gives the axes, the scroll wheel reaches the server in one direction only; at most 30 bit actions), and keep per-player data in c.SetPlayerBytes(p.ID, key, b).
  • Per-player data is replicated to its owner only (component gogame.pdata, tag owner:<id>, at most 64 KiB of JSON per player in all) and saved with the world. A client reads its own with Frame.PlayerBytes(key).
  • What a player must see (HUD values, lists, screens) is written by OnTick into the player's data and played by OnFrame with Frame.UISet, UISetItems, UIShow, UIHide, CameraShake, CameraCut, ParticleBurst, PlaySound, SetMusicContext.
  • UIEvents() events carry Player: the server stamps the sender on every gameui_event.
  • The world seed pins the handshake: the client's -seed (default the project's) must match the server's.

Terrain: Game.Generator#

runtime.generator in vox.project picks one of the engine terrains (biomes, heightmap, flat, empty). To add features of your own (ores that are not in the engine, ruins, a village) or to replace the terrain, set Game.Generator: a function that receives the generator the project describes and returns the one the world uses.

gogame.Main(gogame.Game{
    Generator: func(base worldgen.Generator) worldgen.Generator {
        return &worldgen.Decorated{
            Base: base,
            ID:   "mygame-ores/v1", // bump it when Decorate changes what it generates
            Decorate: func(ctx worldgen.DecorateCtx, c *voxel.Chunk) {
                tin, ok := ctx.Reg.ID("tin_ore") // resolve names here, on the first chunk, not earlier
                if !ok { return }
                // write only voxels of this chunk, from a hash of (ctx.Seed, ctx.Pos)
                c.Set(5, 12, 5, tin)
            },
        }
    },
    // ...
})

worldgen.Decorated keeps what the base terrain offers (chunk layers, registry binding, far-terrain sampling, the biome tint) and adds DecorateCtx.Surface(x, z), the base terrain height in a column, for placing something on the ground from every chunk it overlaps. Rules: the generator is a pure function of (seed, chunk position), safe for concurrent use, with no clock, global state or other random source; a feature wider than a chunk is computed by each chunk it overlaps, from a position hash, and each writes only its own voxels. ID (and ChangesSilhouette, true for a feature that changes the ground seen from afar) are part of the world identity: change the ID whenever the decoration changes, because a saved world would otherwise mix two versions. A generator of your own works too: implement Generate(seed, chunkPos) *voxel.Chunk, WorldID() string and, to receive the registry, WithRegistry(*voxel.Registry) worldgen.Generator. base is nil when the project has no runtime.generator section.

imui reference (burrow-engine/gameui/imui)#

Immediate-mode UI drawn on a render/canvas.Canvas: call widgets every frame, get their result back at once. gogame runs it for you after the declarative game UI; for other hosts call Begin and End yourself.

APIMeaning
New(theme *gameui.Theme) *UInil theme = "dark"
Begin(cv, in Input, w, h), End()frame bracket; Input{MouseX, MouseY, Down, Pressed, Released, Text, Backspace, Enter, Escape}
Window(title, fn)centered, dimmed backdrop, sized to content (a first-frame measure pass runs the body once, idle)
Panel(id, rect, fn)fixed screen rectangle; captures the mouse
Row(fn), Column(fn), Spacer(px)layout; the default flow is a column
Label(text), Image(path, w, h), ProgressBar(frac)display (UI.LoadImage resolves image paths; gogame wires the project files)
Button(label) bool, ButtonID(id, label) booltrue on click (press and release on it)
Checkbox(label, *bool) bool, Slider(label, *float32, min, max) bool, TextInput(id, *string) booltrue when the value changed
Captures() bool, Open() boolmouse over the UI / a Window is shown (gogame frees the cursor then)
Emit(name, value)send a signal to OnTick (journaled, next tick): the only way UI code should change the game

Widget identity is the label (or id) plus its place in the container; use ButtonID when labels repeat or change.
